## 摘要
我们提出了测试驱动的 AI 智能体定义 (TDAD)，这是一种将智能体提示词（prompts）视为编译产物的方法论：工程师提供行为规范，一个编码智能体将其转换为可执行测试，而第二个编码智能体则迭代优化提示词，直到通过测试。在生产环境中部署工具使用型大语言模型（LLM）智能体需要可衡量的行为合规性，而当前的开发实践无法提供这一点。微小的提示词更改会导致隐性回归，工具误用无法被检测到，且策略违规往往在部署后才会显现。为了缓解规范博弈（specification gaming），TDAD 引入了三种机制：(1) 可见/隐藏测试拆分，在编译期间保留评估测试；(2) 语义变异测试，通过编译后智能体生成合理的错误提示词变体，并由测试框架衡量测试套件是否能检测到它们；(3) 规范演进场景，用于量化需求变更时的回归安全性。我们在 SpecSuite-Core 上评估了 TDAD，这是一个包含四个深度规范智能体的基准测试，涵盖了策略合规、落地分析、操作手册遵循和确定性执行。在 24 次独立试验中，TDAD 实现了 92% 的 v1 编译成功率和 97% 的平均隐藏通过率；演进后的规范编译成功率为 58%，其中大多数失败的运行通过了除 1-2 个之外的所有可见测试，并显示出 86-100% 的变异得分、78% 的 v2 隐藏通过率以及 97% 的回归安全得分。该实现已作为开放基准发布于 https://github.com/f-labs-io/tdad-paper-code。

## Abstract
We present Test-Driven AI Agent Definition (TDAD), a methodology that treats agent prompts as compiled artifacts: engineers provide behavioral specifications, a coding agent converts them into executable tests, and a second coding agent iteratively refines the prompt until tests pass. Deploying tool-using LLM agents in production requires measurable behavioral compliance that current development practices cannot provide. Small prompt changes cause silent regressions, tool misuse goes undetected, and policy violations emerge only after deployment. To mitigate specification gaming, TDAD introduces three mechanisms: (1) visible/hidden test splits that withhold evaluation tests during compilation, (2) semantic mutation testing via a post-compilation agent that generates plausible faulty prompt variants, with the harness measuring whether the test suite detects them, and (3) spec evolution scenarios that quantify regression safety when requirements change. We evaluate TDAD on SpecSuite-Core, a benchmark of four deeply-specified agents spanning policy compliance, grounded analytics, runbook adherence, and deterministic enforcement. Across 24 independent trials, TDAD achieves 92% v1 compilation success with 97% mean hidden pass rate; evolved specifications compile at 58%, with most failed runs passing all visible tests except 1-2, and show 86-100% mutation scores, 78% v2 hidden pass rate, and 97% regression safety scores. The implementation is available as an open benchmark at https://github.com/f-labs-io/tdad-paper-code.

### 1. 核心问题与整体含义（研究动机和背景）
随着 LLM 智能体（Agent）进入生产环境，开发者面临三大挑战：**信心不足**（无法验证 Agent 在所有场景下的行为）、**稳定性差**（修改提示词常导致隐性功能回归）以及**集成困难**（评估系统与现有 CI/CD 脱节）。
目前的 Agent 开发主要依赖“试错法”手动调整提示词，缺乏软件工程的严谨性。论文提出了 **TDAD（测试驱动的 AI 智能体定义）**，核心思想是将 Agent 的提示词视为一种“编译产物”，通过将产品需求（PRD）转化为可执行的测试用例，利用编码智能体自动迭代优化提示词，从而实现 Agent 开发的工程化和自动化。

### 2. 方法论：核心思想与技术细节
TDAD 将 Agent 开发模拟为编译器工作流，包含以下核心组件和流程：

*   **核心角色分工**：
    *   **TestSmith**：负责将 YAML 格式的行为规范（Spec）转换为可执行测试（包含可见测试和隐藏测试）。
    *   **PromptSmith**：作为“编译器”，根据可见测试的失败反馈，迭代修改提示词和工具描述，直到通过所有可见测试。
    *   **Built Agent**：最终生成的运行时产物，通过结构化的 `respond` 工具输出结果，便于确定性断言。
    *   **MutationSmith**：评估者，通过生成带有“语义缺陷”的提示词变体（Mutants），检测测试套件的捕捉能力。
*   **关键技术机制**：
    *   **可见/隐藏测试拆分**：防止 PromptSmith 对测试集过拟合（规范博弈）。
    *   **语义变异测试（Semantic Mutation Testing）**：通过故意引入错误逻辑（如“跳过授权检查”），验证测试用例是否能有效识别行为偏差。
    *   **规范演化（Spec Evolution）**：模拟需求变更（V1 -> V2），在不给 PromptSmith 看旧测试的情况下，验证新编译的 Agent 是否保持了旧功能的兼容性（SURS 指标）。
*   **算法流程**：采用双环优化策略。当失败测试较多时进行全局提示词编辑；当失败测试少于阈值（如10个）时，进入聚焦内环，仅针对失败用例快速迭代。

*   **实验规模**：共进行了 **24 次独立试验**（4 个 Spec × 2 个版本 × 3 次重复实验）。

### 6. 主要结论与发现
*   **高成功率**：V1 版本的编译成功率达到 **92%**，平均隐藏测试通过率（HPR）高达 **97.3%**。
*   **回归安全**：在规范演化实验中，回归安全得分（SURS）平均为 **97.2%**，证明该方法能有效保护既有功能。
*   **变异测试价值**：变异测试成功识别了测试套件中的盲点（如 DataInsights V1 中对数字幻觉的检测不足），并在 V2 中得到了修复。
*   **演化挑战**：V2 版本的编译成功率降至 **58%**，主要原因是测试冲突或迭代步数达到上限，但即使失败的运行也通过了 95% 以上的测试。

### 7. 优点与亮点
*   **工程化范式**：首次将软件工程中成熟的 TDD 和变异测试理念完整引入 Agent 开发，解决了提示词工程“黑盒化”的问题。
*   **防博弈机制**：通过隐藏测试和变异测试，有效解决了 LLM 优化过程中常见的“规范博弈”风险。
*   **确定性评估**：通过强制 Agent 使用结构化工具调用（respond tool）和确定性 Mock 数据（Canary values），消除了传统 LLM-as-a-Judge 带来的不确定性。

### 8. 不足与局限
*   **规范依赖性**：TDAD 高度依赖于高质量的 YAML 规范，对于“共情能力”等难以量化的主观行为描述支持较弱。
*   **成本与延迟**：虽然 $2-$3 的成本不算高，但对于需要快速原型开发的场景，30-60 分钟的编译时间可能过长。
*   **模型局限**：实验仅基于 Claude 4.5，尚未验证在其他模型（如 GPT-4o 或开源模型）上的跨模型编译效果。
*   **自检风险**：TestSmith 在生成测试时可能会受到模型安全对齐的限制，难以生成真正的对抗性测试用例。
