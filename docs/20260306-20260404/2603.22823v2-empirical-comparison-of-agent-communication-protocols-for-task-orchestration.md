## 摘要
背景：如今，人工智能智能体系统正从单一工具交互向复杂的多智能体编排转型。因此，出现了两种竞争性的通信协议：一种是规范智能体如何调用外部工具的工具集成协议，另一种是使自主智能体能够相互发现并委派任务的智能体间委派协议。尽管这些协议已被数十家企业合作伙伴在工业界广泛采用，但文献中尚不存在对这些协议的实证比较。目标：本研究的目标是开发首个系统性基准测试，在三个复杂度水平的标准化查询下，比较仅工具集成、多智能体委派以及混合架构，并量化在响应时间、上下文窗口消耗、货币成本、错误恢复和实现复杂度方面的权衡。

## Abstract
Context. Nowadays, artificial intelligence agent systems are transforming from single-tool interactions to complex multi-agent orchestrations. As a result, two competing communication protocols have emerged: a tool integration protocol that standardizes how agents invoke external tools, and an inter-agent delegation protocol that enables autonomous agents to discover and delegate tasks to one another. Despite widespread industry adoption by dozens of enterprise partners, no empirical comparison of these protocols exists in the literature. Objective. The goal of this work is to develop the first systematic benchmark comparing tool-integration-only, multi-agent delegation, and hybrid architectures across standardized queries at three complexity levels, and to quantify the trade-offs in response time, context window consumption, monetary cost, error recovery, and implementation complexity.

*   **研究动机**：随着 AI 智能体从简单的工具调用转向复杂的多智能体协作，行业内出现了两种竞争性的通信范式：一种是以 Anthropic 为代表的 **MCP**（标准化工具调用），另一种是以 Google 为代表的 **A2A**（智能体间任务委派）。
*   **核心问题**：尽管这两种协议已被企业广泛采用，但学术界缺乏关于它们在不同任务复杂度下的性能（延迟、成本、上下文消耗）对比的实证数据。开发者在选择架构时往往依赖直觉而非数据。

### 2. 方法论：核心思想与架构设计
论文设计了三种等效的架构来处理相同的业务逻辑（开源项目健康度分析）：
*   **架构 A (仅 MCP)**：单智能体架构。一个核心智能体通过 stdio 传输协议连接四个 MCP 工具服务器。所有工具返回的数据都堆叠在同一个上下文窗口中。
*   **架构 B (A2A 多智能体)**：分布式架构。一个协调者智能体通过 HTTP/JSON-RPC 将子任务委派给四个专门的智能体（GitHub、npm 等专家）。每个专家拥有独立的上下文窗口。
*   **架构 C (混合架构)**：引入一个轻量级的启发式路由层。根据查询关键词预判复杂度，简单查询走 MCP，复杂查询走 A2A。
*   **关键技术细节**：A2A 架构利用了“上下文隔离”思想，而 MCP 遵循“单窗累积”模式。

### 3. 实验设计与基准测试
*   **实验场景**：开发了一个“开源健康分析器”，对接 GitHub、npm、OSV.dev 和 Stack Overflow 四个真实 API。
*   **基准测试 (Benchmark)**：定义了 30 个标准化查询，分为三个难度等级：
    *   **简单**：单数据源、单项目。
    *   **中等**：多数据源、单项目。
    *   **复杂**：多数据源、多项目对比。
*   **对比方法**：在相同模型（Claude 3.5 Sonnet）下，对三种架构进行交叉对比。
*   **评估指标**：端到端延迟、总 Token 消耗、货币成本、API 调用次数、代码复杂度（LOC 和循环复杂度）。

### 4. 资源与算力
*   **模型使用**：所有实验均使用 `claude-sonnet-4-20250514`。
*   **硬件环境**：实验在一台机器上运行，所有 A2A 智能体部署在 `localhost` 以消除网络波动干扰。
*   **算力说明**：文中未提及具体的 GPU 训练算力，因为该研究侧重于推理阶段的编排性能而非模型训练。

### 5. 实验数量与充分性
*   **实验规模**：共执行了 **450 次受控实验**（30 个查询 × 3 种架构 × 5 次重复执行）。

### 6. 主要结论与发现
*   **性能交叉效应 (Crossover Effect)**：
    *   在**简单任务**中，MCP 显著优于 A2A（延迟 8.9s vs 19.8s），因为 MCP 没有 HTTP 通信和委派开销。
    *   在**复杂任务**中，A2A 反超 MCP（延迟 45.1s vs 51.8s），且 **Token 消耗仅为 MCP 的 1/3 左右**。
*   **上下文膨胀 (Context Bloat)**：量化了单智能体架构在处理复杂任务时的缺陷——MCP 会导致上下文窗口迅速堆叠，而 A2A 通过分布式窗口保持了每个智能体的“精简”，从而将复杂任务的成本降低了 **39%**。
*   **混合架构优势**：混合架构在所有复杂度下都能追踪到最优表现，证明了动态路由的实用性。

### 7. 论文亮点
*   **首次实证**：填补了 MCP 与 A2A 协议对比的空白，提供了宝贵的基准数据。
*   **互补性证明**：科学地证明了 MCP 和 A2A 不是竞争关系，而是互补关系（MCP 适合“智能体-工具”交互，A2A 适合“智能体-智能体”编排）。
*   **决策框架**：为开发者提供了一个清晰的决策流程图，具有极高的工程实践指导价值。

### 8. 不足与局限
*   **模型单一性**：实验仅基于 Claude 系列模型，结果在其他模型（如 GPT-4o 或开源模型）上的泛化性有待验证。
*   **网络环境理想化**：A2A 运行在 localhost，忽略了真实生产环境中的跨服务器网络延迟，这可能会推迟 A2A 性能反超 MCP 的临界点。
*   **领域局限**：仅测试了开源项目分析一个领域，其他领域（如多模态或长文本处理）的特征可能不同。
*   **样本量限制**：每组查询仅重复 5 次，虽然统计学上显著，但对于捕捉长尾分布的异常情况可能不足。
