## 摘要
多智能体系统应如何设计？这种设计知识能否以一种可检查、可修订且可迁移的形式被捕获？我们介绍了 ABSTRAL，这是一个将多智能体系统（MAS）架构视为不断演进的自然语言文档的框架，该文档是通过对比轨迹分析进行细化的产物。研究得出了三项发现：首先，我们对多智能体协调成本进行了精确测量：在固定轮数预算下，集成系统仅达到 26% 的轮数效率，66% 的任务耗尽了限制，但通过发现可并行的任务分解，其表现仍优于单智能体基准。其次，编码在文档中的设计知识具有可迁移性：在一个领域学习到的拓扑推理和角色模板为新领域提供了先发优势，迁移后的种子在单次迭代中即可达到冷启动第 3 次迭代的性能。第三，对比轨迹分析能够发现初始设计中不存在的专家角色，这是以往系统均未展示出的能力。在 SOPBench（包含 134 个银行任务，具有确定性真值）上，以 GPT-4o 为骨干模型的 ABSTRAL 达到了 70% 的验证集通过率和 65.96% 的测试集通过率。我们将收敛后的文档作为可检查的设计原理予以发布。

## Abstract
How should multi-agent systems be designed, and can that design knowledge be captured in a form that is inspectable, revisable, and transferable? We introduce ABSTRAL, a framework that treats MAS architecture as an evolving natural-language document, an artifact refined through contrastive trace analysis. Three findings emerge. First, we provide a precise measurement of the multi-agent coordination tax: under fixed turn budgets, ensembles achieve only 26% turn efficiency, with 66% of tasks exhausting the limit, yet still improve over single-agent baselines by discovering parallelizable task decompositions. Second, design knowledge encoded in documents transfers: topology reasoning and role templates learned on one domain provide a head start on new domains, with transferred seeds matching coldstart iteration 3 performance in a single iteration. Third, contrastive trace analysis discovers specialist roles absent from any initial design, a capability no prior system demonstrates. On SOPBench (134 bank tasks, deterministic oracle), ABSTRAL reaches 70% validation / 65.96% test pass rate with a GPT-4o backbone. We release the converged documents as inspectable design rationale.

### ABSTRAL：通过迭代细化与拓扑优化的多智能体系统自动设计

#### 1. 核心问题与整体含义（研究动机和背景）
当前多智能体系统（MAS）的设计主要依赖人工经验。现有的自动化设计方法通常将中间知识存储为代码、提示词（Prompts）或技能库，这些形式往往是“黑盒”，缺乏可解释性、难以手动修订且无法在不同领域间有效迁移。
论文的核心问题是：**自然语言文档能否作为多智能体设计的优化目标？** 研究者希望通过一种可读、可编辑的 Markdown 格式（`SKILL.md`）来捕获设计知识，使系统能够自动演进架构、发现新角色并优化拓扑结构。

#### 2. 方法论：核心思想与技术流程
ABSTRAL 框架将 MAS 架构视为一个动态演进的自然语言文档，通过三层循环进行优化：

*   **内层循环（轨迹驱动细化）：**
    *   **构建（Build）：** 元智能体（Meta-agent）读取 `SKILL.md` 生成智能体规范（AgentSpec）。
    *   **运行（Run）：** 在沙盒环境中执行任务，捕获详细的执行轨迹（Traces）。
    *   **分析（Analyze）：** 对比失败与成功的轨迹，将错误归类为五种证据类别（EC1：领域知识错误；EC2：拓扑/路由错误；EC3：角色缺失；EC4：接口不匹配；EC5：成功模式）。
    *   **更新（Update）：** 根据分类结果针对性地修改 `SKILL.md` 的四个部分（领域知识 K、拓扑推理 R、角色模板 T、构建协议 P）。
*   **中层循环（收敛与整合）：** 监控性能平台期，并在每 5 次迭代后进行“整合”（Consolidation），合并冗余规则并压缩文档，防止语义漂移和规则膨胀。
*   **外层循环（拓扑多样性探索）：** 利用**图编辑距离（GED）**和**语义嵌入距离**作为排斥约束，强制系统探索性质完全不同的拓扑家族（如从层级式转向集成式），避免陷入局部最优。
*   **专家角色发现（EC3）：** 当发现单个智能体处理了结构上不兼容的子任务时，系统会自动推断并创建一个具备特定“认知立场”（如验证者、执行者）的新专家角色。

#### 3. 实验设计
*   **数据集/场景：** 使用 **SOPBench**（2025），包含 134 个银行领域的标准作业程序（SOP）合规性任务。
*   **评估标准（Benchmark）：** 采用确定性 Oracle 评估（5 项布尔准则：无工具调用错误、无约束违反、数据库匹配、先决条件满足、目标动作正确）。
*   **对比方法：** 
    *   发布基准：GPT-4o-mini, GPT-4o, Claude-3.7-Sonnet, o4-mini-high 等单智能体基准。
    *   消融实验：ABSTRAL 仅内层优化（固定拓扑） vs. ABSTRAL 全框架（带外层拓扑搜索）。
    *   知识迁移实验：对比“冷启动”与“携带已学习知识启动”的性能差异。

#### 4. 资源与算力
*   **模型使用：** 元智能体使用 **Claude 3.5 Sonnet**；执行智能体骨干使用 **GPT-4o**。
*   **算力/成本：** 
    *   总计 24 次迭代（3 外层 × 8 内层）。
    *   消耗约 **15.4 万个 Token**，总 API 成本约 **5 美元**。
    *   总时长 **28.4 小时**，其中 79% 的时间用于任务运行（RUN 阶段），元智能体分析仅占 21%。
*   **硬件环境：** 实验在具备 2GB RAM 的沙盒环境中运行，未提及具体 GPU 型号（因主要依赖 API）。

#### 5. 实验数量与充分性
*   **实验规模：** 进行了 24 轮迭代优化，涵盖了验证集（40 题）和测试集（94 题）。
*   **充分性：** 包含了详细的消融实验（证明了外层循环对性能提升的贡献）和知识迁移实验（证明了 `SKILL.md` 的可复用性）。
*   **客观性：** 使用确定性 Oracle 而非“LLM-as-judge”，保证了评估的客观性。但论文也承认，由于样本量和随机性，不同运行批次间存在约 5% 的性能波动。

#### 6. 主要结论与发现
*   **协调税（Coordination Tax）：** 首次精确量化了多智能体开销。在固定轮数预算下，MAS 的轮数效率仅为 **26%**（大量轮数消耗在路由和分发上），66% 的任务会触及轮数上限。
*   **性能提升：** 尽管有协调税，但通过并行化分解任务，ABSTRAL 在 SOPBench 银行任务上达到了 **65.96%** 的测试通过率，优于 GPT-4o 单智能体基准（58.96%）。
*   **知识迁移：** 在一个领域学到的设计知识（`SKILL.md`）可以显著加速新领域的优化，迁移后的种子在第 1 次迭代即可达到冷启动第 3 次迭代的水平。
*   **角色发现：** 成功通过对比分析自动发现了初始设计中不存在的专家角色（如“外汇专家”、“信用申请验证者”）。

#### 7. 优点
*   **高可解释性：** 优化目标是 Markdown 文档，人类可以直接阅读、理解并修改设计逻辑。
*   **拓扑感知：** 不同于以往只优化 Prompt 的系统，ABSTRAL 能自动在层级、集成、管道等不同拓扑结构间搜索。
*   **量化深度：** 对多智能体系统的“协调成本”给出了直观且科学的量化分析，具有很强的工程指导意义。

#### 8. 不足与局限
*   **框架开销：** 使用 LangGraph 等框架引入了额外的节点转换开销，导致与原始 API 调用基准对比时存在一定的不公平性（Confounds）。
*   **随机性风险：** 实验结果基于单次运行，验证集批次较小（20 题），可能存在采样偏差。
*   **拓扑覆盖：** 预设的 7 种角色分类和拓扑家族可能无法涵盖所有可能的复杂架构。
*   **任务类型限制：** 实验表明 MAS 主要在可并行化的任务中占优，对于长链条顺序任务，协调税可能导致性能下降。
