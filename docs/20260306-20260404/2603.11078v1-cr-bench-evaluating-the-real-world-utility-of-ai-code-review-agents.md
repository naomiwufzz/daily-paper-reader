## 摘要
前沿大语言模型的最新进展使得代码审查智能体能够在开放式、推理密集型的场景中运行。然而，由于缺乏标准化的基准测试和细粒度的评估协议，除了粗粒度的成功指标外，很难评估代码审查智能体的行为，特别是对于误报成本高昂的任务。为了填补这一空白，我们引入了 CR-Bench（一个基准数据集）和 CR-Evaluator（一个针对代码审查智能体的细粒度评估流水线）。利用这些工具，我们进行了一项初步研究，在两个前沿模型上评估了单次（single-shot）智能体和基于 Reflexion 的智能体。我们发现，当代码审查智能体被设计为识别所有隐藏问题时，可能会表现出较低的信噪比；如果仅通过解决率来衡量，这会掩盖真实的进展和开发人员的生产力。我们的分析确定了问题解决与虚假发现之间隐藏的权衡，揭示了限制有效智能体设计的前沿边界。总之，随着基于大语言模型的系统从受控的基准测试转向现实世界的软件工程工作流，CR-Bench 和 CR-Evaluator 为研究和开发代码审查智能体提供了及时的基础。

## Abstract
Recent advances in frontier large language models have enabled code review agents that operate in open-ended, reasoning-intensive settings. However, the lack of standardized benchmarks and granular evaluation protocols makes it difficult to assess behavior of code review agents beyond coarse success metrics, particularly for tasks where false positives are costly. To address this gap, we introduce CR-Bench, a benchmarking dataset, and CR-Evaluator, a fine-grained evaluation pipeline for code review agents. Using these tools, we conduct a preliminary study evaluating both a single-shot agent and a Reflexion-based agent across two frontier models. We find that code review agents can exhibit a low signal-to-noise ratio when designed to identify all hidden issues, obscuring true progress and developer productivity when measured solely by resolution rates. Our analysis identifies the hidden trade-off between issue resolution and spurious findings, revealing a frontier that constrains effective agent design. Together, CR-Bench and CR-Evaluator provide a timely foundation for studying and developing code review agents as LLM-based systems transition from controlled benchmarks to real-world software engineering workflows.

### 1. 核心问题与研究动机
*   **研究背景**：尽管大语言模型（LLM）已被广泛用于代码审查，但现有的评估基准存在两大缺陷：一是将客观的逻辑错误与主观的风格偏好（如缩进、命名）混为一谈；二是多基于合成数据或单文件片段，缺乏真实世界大规模仓库的复杂上下文。
*   **核心问题**：代码审查中存在严重的“偏差-方差权衡”。智能体若追求高召回率（发现所有 Bug），往往会产生大量噪声（误报），导致开发者产生审美疲劳并降低生产力。行业急需一个专注于**客观缺陷检测**且能衡量**信噪比**的评估框架。

### 2. 方法论：CR-Bench 与 CR-Evaluator
*   **CR-Bench 构建流程**：
    1.  **数据源转化**：从 SWE-Bench 出发，利用 `git blame` 和 GitHub API 回溯修复特定 Issue 的原始 Pull Request（PR）。
    2.  **可预防性筛选**：使用 LLM 过滤掉新功能开发或重构，仅保留那些“如果审查更仔细就能预防”的逻辑缺陷（Preventable Defects）。
    3.  **多维分类体系**：引入分类学标签，包括**根因类别**（如结构、数据、并发等）、**下游影响**（如可靠性、性能、安全等）和**严重程度**（高、中、低）。
*   **CR-Evaluator 评估流水线**：
    *   采用 **LLM-as-a-judge**（使用 Claude-Sonnet-4.5）对智能体生成的评论进行三类标注：
        *   **Bug Hit**：准确识别出目标缺陷。
        *   **Valid Suggestion**：虽未击中目标 Bug，但提供了有价值的改进建议。
        *   **Noise**：事实错误、无关痛痒或幻觉内容。
    *   **核心公式**：
        *   **Usefulness Rate（有用率）** = (Bug Hits + Valid Suggestions) / Total Reviews
        *   **SNR（信噪比）** = (Bug Hits + Valid Suggestions) / Noise Count

*   **实用导向**：首次将“信噪比（SNR）”作为代码审查智能体的核心指标，直击开发者在生产环境中的痛点。
*   **上下文完整**：不同于以往的方法级基准，CR-Bench 提供了完整的 PR 上下文（包括描述、多文件 Diff 和元数据）。
